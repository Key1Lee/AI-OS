# Root-cause investigation

Treat `/debug` and requests to diagnose an unexplained discrepancy as native, tool-capable agent work under `AGENTS.md`. [Test](testing.md) can expose a failure; Debug establishes causality; Implementation changes the system; [Verify](verification.md) proves corrected behavior. This guidance is not a Skill, command runner, or permission grant. The shared `py_dev` model runner has no repository tool executor, so its model output alone cannot establish a repository root cause.

## Activation and scope

Start with the expected behavior, observed behavior, affected scope, and the evidence that shows a discrepancy. Unexpected test or runtime failures, regressions, local versus staging differences, conflicting traces, intermittent behavior, and unexplained Verify failures belong here when their cause is unknown. When active material service impact is suspected, [Incident](incident.md) coordinates impact assessment and stabilization while Debug investigates cause. A difficult implementation, new feature, request to run tests, acceptance verification, completed-change review, architecture audit, or explanation of working code does not by itself start Debug. Explicit `/debug` asks for this investigation, but the result may be a requirement change rather than a defect.

Use the smallest relevant working set. Follow affected project instructions and existing tests. For shared runtime problems, [runtime guidance](runtime.md) identifies local Qwen `/health`, `/v1/models`, and `/props` probes and safe run traces (`~/.config/py-dev/run-traces.jsonl`, `AIOS_TRACE_FILE`). [Model router guidance](model-router.md) identifies per-attempt audit records (`~/.config/py-dev/model-audit.jsonl`, `MODEL_AUDIT_FILE`). Those records omit prompt bodies and secrets; application and project logs or state remain project-owned. Read only relevant diagnostic data and preserve existing access boundaries.

## Investigation and evidence

Observe, reproduce when useful, narrow the failure boundary, compare a small set of plausible causes, and choose the cheapest experiment that distinguishes them. Record **FACT** for direct observations, **ASSUMPTION** for unverified premises, **HYPOTHESIS** for possible causes, **EXPERIMENT** for a diagnostic intervention, and **RESULT** for its observed output. A recent commit, stack location, or plausible story is not causal proof. Mark **CONFIRMED ROOT CAUSE** only when the condition exists, explains the symptom, and a controlled comparison, intervention, or equally strong isolation supports the causal link. Otherwise report **UNRESOLVED**, the attempted checks, remaining hypotheses, missing evidence, and the next discriminating observation. Keep diagnostic changes temporary and narrow; remove them before handoff or justify retained instrumentation as a separate approved change.

When reproduction fails, record tested conditions and missing historical evidence. For competing explanations, identify an observation that would separate them. For intermittent or concurrent behavior, compare controlled timing, ordering, shared state, retry, and resource evidence before claiming a race. For environment-specific behavior, compare relevant configuration, versions, permissions, schema/data state, and external dependencies. A third-party error confirms a failure at that boundary, not the provider's internal cause. For stateful failures, inspect the relevant invariant and safe state without mutating production data; use dated baseline evidence before calling a failure pre-existing. If observability is insufficient, identify the exact missing signal and use minimal safe capture when permitted; substantial instrumentation goes to Plan. Do not mask an unknown cause with speculative code changes or retries.

## Outcome and handoff

Report expected versus observed behavior, scoped evidence, experiments and results, causal conclusion or uncertainty, affected component, and a reproduction or regression condition. A confirmed defect within approved scope goes to **Implementation** with the corrective behavior needed. A false material Plan assumption, new requirement, or change to architecture, scope, contract, security, or persistence goes to **Plan** with the conflicting evidence and decision needed. If behavior matches the approved contract and the request is new, call it a **REQUIREMENT CHANGE**, not a defect. An unresolved cause remains in Debug with a next evidence step; do not invent a repair handoff. After correction, return through [Verify](verification.md) and then [Review](review.md) as applicable.

## Evaluation and limits

`evals/debug-cases.toml` holds 13 positive and 8 negative routing and diagnostic-reasoning fixtures. In a local Qwen label-only routing trial, a basic workflow prompt chose correctly for 20/21 cases and a short Debug boundary instruction for 21/21. In a separate diagnosis prompt that primed Debug, both versions wrongly activated all eight negative controls; the short instruction improved normalized diagnosis labels from 11/13 to 13/13 and positive-case handoffs from 4/13 to 12/13. These are small, stipulated-evidence prompt trials, not a qualification of the model as a debugger. The mirrored-script case additionally has a live repository reproduction with a controlled import-path intervention. Model-only calls cannot inspect or change this repository, and Codex and Claude were not separately benchmarked. The guidance therefore belongs with the tool-capable agent rather than in a new Skill runner path.
