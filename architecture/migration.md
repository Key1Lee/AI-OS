# System transitions

Treat `/migrate` or a concrete request to move an existing system to a new version, schema, API, dependency, provider, or architecture as a specialized **Plan → Implement** task under `AGENTS.md`. Migration is optional, not another required lifecycle stage or a shared executable command. The objective is to move an identified source state to a defined target state while controlling relevant invariants, compatibility, sequence, recovery, and completion. A [refactor](refactoring.md) instead preserves the existing intended external contract while changing internal structure. A small, low-risk upgrade can proceed as ordinary Implementation.

## Define the transition

Before a material migration, record the current implementation/version and affected contracts, data, producers, consumers, and operating constraints; the intended replacement and contracts; and observable completion conditions. Inspect only affected paths. Resolve a materially ambiguous target, breaking-contract decision, or rollout design in Plan before broad edits. Use a plan for schema or data changes, multi-service transitions, framework/runtime replacement, irreversible steps, or material rollout risk; keep a trivial upgrade lightweight.

Select only invariants at risk, such as data integrity, authorization, compatibility, availability, ordering, retry/idempotency behavior, or contractually important performance. Choose the simplest strategy that protects them. Direct replacement is sufficient when no transition state is needed. Otherwise define ordered, independently checkable phases and the temporary compatibility state: for example an adapter, expand-and-contract schema, backfill and cutover, feature flag, or phased consumer move. State which steps are reversible and how to recover from material-risk steps. An irreversible data change needs a snapshot/restore or roll-forward and reconciliation decision; do not promise rollback that cannot work. For stored data, address batching, retries, resume points, duplicate prevention, validation, and temporal/default semantics only where they matter.

## Execute and close

Implementation owns code edits and local checks. Reuse project-owned migration mechanisms and deployment instructions. Use an existing deterministic tool, or a tested codemod, for an exact repetitive transformation; use agent reasoning for semantic or compatibility decisions. Do not create a shared migration runner or model-specific workflow for one project's transition. Each meaningful phase should leave a coherent state where feasible. Preserve failing evidence and stop advancing phases when an invariant fails; active material service impact goes to [Incident](incident.md), unknown causes to [Debug](debug.md), and invalidated strategy or target decisions to Plan.

Generating code, local testing, rollout preparation, staging execution, production execution, and destructive schema/data operations are separate actions. Implementing migration code does not authorize production or destructive execution. Follow the affected project's permissions and runbook; use preview, dry run, or a safe copy when available. Obtain authorization for production-impacting or destructive execution unless already explicitly granted.

Completion requires evidence for the target state and relevant invariants, not merely a passing compile or the presence of a new path. Hand the changed scope, source/target contract, phase status, temporary compatibility state, recovery path, checks, and gaps to independent [Verify](verification.md); then [Review](review.md) inspects material risk and unnecessary transitional complexity. Remove an old path, adapter, flag, dual read/write, schema, or dependency only when evidence shows consumers no longer need it. Otherwise name the remaining phase and exit condition. [Test](testing.md) supplies reproducible check evidence; AI-OS-wide [Audit](../skills/audit/SKILL.md) remains a different task.

## Existing repository mechanisms

Northstar owns ordered SQL files and n8n workflow imports in `projects/Northstar/northstar-leadops/`; its offline validation does not prove live PostgreSQL, n8n, or external-service behavior. Toptal-Testing owns SQLite `PRAGMA user_version` handling and pre-upgrade backup in `projects/Toptal-Testing/training/persistence.py`. Both remain project-owned. The shared `py_dev` model runner has no repository tool executor or rollout authority, so it cannot perform or certify a migration from a prompt.

`evals/migration-cases.toml` records 18 routing and eight transition-boundary cases. In one local Qwen label-only comparison at temperature zero, a basic workflow prompt scored 15/18 routing and 6/8 boundary labels; adding a short migration boundary instruction scored 17/18 and 8/8. Both still routed a known bug to Debug. The rollout-sensitive fixture was clarified after its original wording reasonably invited Plan, and its two labels were rerun. The trial shows useful guidance, but it does not execute code, inspect repository evidence, validate rollout safety, or establish Codex/Claude behavior. A standalone Skill would duplicate the native Plan/Implement boundary without adding tool authority or project migration machinery, so the guidance remains a focused reference.
