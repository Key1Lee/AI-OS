# Release readiness and delivery

Treat `/release` or a request to prepare or assess a change for delivery as a native, tool-capable agent task under `AGENTS.md`. It is an optional decision after implementation, not another coding stage, shared release command, or authorization to deploy. The task is to identify the intended release scope and target, decide whether existing evidence satisfies the affected project's release requirements, prepare required artifacts using project-owned mechanisms, and coordinate any authorized rollout and bounded follow-up checks.

## Readiness decision

Start with the intended changed files or commit range, project/component, artifact, and release target if specified. Inspect the affected project's instructions, actual changes, available release procedure, version policy, and environment constraints. Do not infer production from the word *release*. If the target or required business policy is material and undecided, return the decision to Plan. Detect unrelated changes before including them in an artifact.

Select prerequisites by scope and risk: approved behavior, completed implementation, independent [Verify](verification.md) evidence for the applicable contract, [Review](review.md) findings and their disposition, project checks, build/package result, version and dependency constraints, documentation or release notes, required [migration](migration.md) phases, rollout observability, recovery path, and required approvals. Consume still-valid Verify and Review evidence; do not rerun their full work merely to produce a release report. A green build alone does not establish readiness. If evidence is missing or a blocking gate fails, state the exact gap and do not advance that release. Route active material service impact to [Incident](incident.md), a known implementation defect to Implementation, unexplained causality to [Debug](debug.md), changed requirement or strategy to Plan, and corrected code back through Verify and Review where applicable.

Report the scope and target, evidence used, unmet gates, candidate artifact/version and release-note status where required, rollout and recovery method, authorization status, and a clear readiness result: **READY** for the specified authorized next action, **PREPARED / APPROVAL REQUIRED** when safe preparation is complete but an action needs authorization, or **NOT READY** with blockers. Do not call a release completed until the authorized delivery and required bounded post-release checks actually succeed. If there is no repository release policy for the requested target, state that gap rather than inventing one.

## Use project mechanisms

Use existing build, package, version, tag, checksum, manifest, deployment, and health-check tooling where present. Add deterministic tooling only for a concrete repeatable gap; do not create a shared CI/CD or packaging framework for heterogeneous projects. Base release notes on the actual diff and verified behavior, distinguishing user-visible changes, breaking changes, migration steps, and operator actions. Do not change versions or tags without policy or task authorization. Choose direct or staged rollout according to actual blast radius, data impact, reversibility, and project mechanisms. For a migration-dependent release, consume its phase order, compatibility requirements, and recovery path; do not replace them with a second plan or remove adapters before their exit conditions hold.

Preparing a summary, generating a candidate, running local checks, drafting a release/tag, staging, production publication/deployment, and irreversible production operations are separate actions. A `/release` request alone does not authorize production-impacting or destructive actions. Finish safe, reviewable preparation first and obtain the required project/user authorization for the specific action unless it was already explicitly granted. After an authorized deployment, run the smallest project-defined smoke or health check and inspect relevant failure indicators for the agreed window; stop at a failed gate and use the established recovery method. Do not promise rollback across irreversible data steps or start indefinite monitoring.

## Current repository evidence

The shared AI-OS root has no Git checkout, repository-wide CI/CD, version/tag automation, package release policy, or production release command. Northstar has project-owned offline checks, n8n workflow exports, a local Docker Compose health check, and documented import, test, and publish steps; its offline checks do not prove live integrations, and its process document names business decisions required before production launch. Toptal-Testing documents a loopback local launcher and prohibits deployment without authorization. Neither project's mechanism should be promoted into a universal release pipeline. The shared `py_dev` Skill runner has no repository tool executor or release authority.

`evals/release-cases.toml` records 18 routing and ten gate-decision fixtures. In one local Qwen label-only comparison at temperature zero, a basic workflow prompt scored 16/18 routes and 5/10 gate actions; a short release boundary instruction scored 17/18 and 8/10. The instructed prompt still treated a local backup archive as Implementation and missed the existing-builder and post-deployment-check actions. These stipulated labels do not inspect a diff, build an artifact, validate a target environment, or establish Codex/Claude reliability. They support concise boundary guidance, not a standalone Skill or a release verdict from the model-only runner.
