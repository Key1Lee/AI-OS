# Completed-change review

Treat `/review` or a request for final engineering review as a native agent task under `AGENTS.md`. There is no separate Review Skill or review runner. Review normally follows [Verify](verification.md). Start with the implementation diff or known changed-file set, directly affected code, objective and approved scope, and the verification result when available. Treat the implementation summary as orientation and the current code as evidence. Inspect additional contracts, callers, and architecture guidance only where the change warrants it. If the changed scope cannot be established, state that coverage gap.

Review asks whether the completed change introduces a material risk beyond what acceptance verification and existing checks establish. Trace relevant changed behavior and boundaries, then validate candidate findings against the repository. Select risk dimensions by the change: correctness and regression, architecture ownership, security, reliability, data integrity, or maintainability. Give greater depth to authorization, persistent data, concurrency, public APIs, and shared interfaces. Use [Security Review](security-review.md) when the request or changed trust boundary warrants focused attacker-path validation. For a [migration](migration.md), inspect compatibility risk and temporary transition mechanisms against their exit conditions. A small local diff needs a focused review. Reuse test, lint, type, schema, static, or security results when relevant; do not rerun the full verification workflow or duplicate those tools. If Verify remains partial or blocked, report that separately without turning Review into an acceptance verdict.

Report material, evidence-supported findings, ordered by impact. Each finding names its file and location, the observed issue, supporting evidence, likely consequence, and a useful correction direction. Mark it **confirmed** when repository evidence supports the issue or **credible risk** when impact still needs investigation. Keep useful optional **suggestions** separate from material findings. Use **Blocking** for credible correctness, security, data-loss, contract, or major regression issues; **Important** for material engineering risk; and **Suggestion** for optional improvement. Do not present a possibility as a confirmed defect. Ignore formatting and minor style noise. A clean result may say **No material findings** with the inspected scope and any material coverage limit.

Review inspects and reports; it does not silently modify implementation, tests, or contracts. Send straightforward confirmed defects to Implementation, unexplained observed behavior to [Debug](debug.md), and invalidated scope or architecture assumptions to Plan. A material structural issue may motivate a scoped [refactor](refactoring.md), but an optional style preference does not. A corrected change returns through Verify where applicable before final Review. Keep AI-OS-wide conformance with Audit. A request to run a check, prove acceptance criteria, debug a failure, plan work, or explain code does not start this review workflow.

The shared `py_dev` model runner has no repository tool executor. On ten stipulated-diff classification cases, the local Qwen baseline and a trial thin review instruction each identified all six material-risk cases but also reported findings for all four clean or style-only cases. In an eighteen-case intent probe, the baseline routed 16 correctly and a short boundary instruction routed 18 correctly. Better routing did not fix finding noise. This route is not qualified for final independent review; use a tool-capable agent. Codex and Claude review behavior has not been separately benchmarked, and optional cloud adapters were not called. [Review fixtures](../evals/review-cases.toml) record ten positive and eight negative intent cases; they do not replace real diff inspection.
